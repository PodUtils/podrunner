# Accepted residuals

The risks that the design accepts. Each one names the decision that
accepts it and what would remove it. GitHub #4 (DR-4, Q1 of
`TODO/PROGRESS.md`) links this list.

| # | Residual | Accepted by | What removes it |
| --- | --- | --- | --- |
| R1 | A trusted job on a no-root host runs at boundary `redirect`: path rewriting, no isolation against hostile code. A compromised dependency can read the files of the uid and reach the host. | DR-4, yes (2026-11-11), for all trusted repositories, only when the operator sets `[tier.trusted] min_boundary = "redirect"`, with the mitigations of T-045. pmask can later cut the same-uid reads of other jobs (DR-6). | The `confined` boundary (T-042, `pod-confine`). |
| R2 | On a shared principal, a unit can signal and read the other processes of the uid, also podrunner and the control socket. One unit at a time limits it to the job that runs and the next one. | The design of `slots` (T-021) | A distinct principal for each unit. On a podvm unit of the supervise rung, `[unit.podvm] confine = true` denies `/proc/PID/environ`, `root` and `cwd` of the other processes of the uid (T-079). |
| R3 | A trusted job of a member gets the secrets of its repository, also when a dependency in it is hostile. | The tier rule (T-018) | Nothing in podrunner: the forge owns secrets. |
| R4 | A compromised `mint` host or sidecar has each credential of its source. | The process rule (`threat-model.md`) | The runbook (`leak-runbook.md`) limits the time. |
| R5 | The `advisory` hold (`podnet pod --backend seccomp`) does not hold unix, netlink and vsock sockets, loopback TCP and inherited descriptors (T-044). A trusted payload can go around it. | `trusted` needs `advisory` only | The netns hold (`enforced`, T-041) on a host with user namespaces and `/dev/net/tun`. On a host with neither, R5 stays. |
| R6 | The lock of a state directory is a `flock`. On a network filesystem it may give no protection, so two hosts that share one state directory can both run `serve` and destroy the units of the other. | GitHub #54: one host for each state directory | A lease with a clock, if a shared state directory is ever needed. |
| R7 | Each step of a job can read the credential of its runner: the runner reads its files (`.runner`, `.credentials`, `.credentials_rsaparams`) from its root as the user of the job, so a step can read them too, on each kind (`secret_delivery: files` in `kinds[].probe` of `status --json`). With it a step can act as the runner for the life of the JIT configuration: one job, as GitHub binds it (T-175). | The design of the official runner (SPEC; githome's G-03, T-519) | A runner that keeps its credential out of the reach of its steps; not in the official runner. |
| R8 | With `pull_request_target` in `[trust] extra_events`, a job of that event runs trusted with the secrets of its repository. Its workflow comes from the base branch of the pull request: each branch that a pull request can target, not only the default branch. A step can check out and run the code of the pull request. The rule takes only a pull request whose head is the repository itself (not a fork: another repository, also the root of the fork network) and whose actor is a member. The actor is the account that triggered the event, not the author of the code: a member who labels, reopens or marks ready a pull request of another account with write access makes that code run trusted, with the secrets. | Q12 (the owner, 2026-11-24): an opt-in, off by default (T-518). `check`, `serve` and `mint-serve` print one line that names it. An agent's job of the event from a fork, or with an unknown head, is refused, also on an untrusted set. | Not to list `pull_request_target`. Keep a reviewed workflow on each branch that can take a pull request. |
| R9 | For `workflow_run`, `issue_comment`, `repository_dispatch` and `release`, the run object of GitHub has the same repository as head and as base, so `head_is_fork` is `no` for each job of these events, also when the code that the job runs comes from a fork. Only the actor (`member`) and the owner guard such a job. A member who triggers the event (a comment, a dispatch, a release) makes the workflow run trusted, with the secrets, and the workflow decides what code it runs. | Q5 (the owner, 2026-11-13): the events are an opt-in, off by default (`[trust] extra_events`). `check`, `serve` and `mint-serve` print one line that names each listed event (T-518). | Not to list these events on a repository whose workflow for them checks out or runs code of a pull request. Keep such a workflow reviewed. |
