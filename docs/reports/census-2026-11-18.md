# The census of T-491 (2026-11-18)

Two read-only agents compared each ask of githome (G-01 to G-41) and of cfb
(A-X-01, A-V-11, P-1 to P-8, R-051 to R-054, C1 to C5) with `main` at
`d72b161` and the release `v0.1.0-beta.7` (`129310e`). This page is a
reading at a time: the record (`TODO/`) holds the work. T-491 lists the
entry of each gap.

Corrections of the lead session after a check of the code:

- G-27 ("`on_cancel` drops a cancel in `Matched`, `Claimed` and
  `Minted`"): not reachable. `intake` runs the placement, the claim, the
  mint and the start in one call (`engine.rs`, `run.rs`), so a cancel
  meets `Offered`, `Started` or `Running` only. A test that stops after
  one poll sees `Started`. T-502 keeps the other parts.
- The disk bound of an offer above `disk_max_bytes` lifted the bound of
  the operator (`disk.rs`): fixed in the same commit as this page, with
  the test `the_disk_of_an_offer_does_not_lift_the_bound_of_the_kind`.

### Gaps with no entry

1. **G-05/G-06: the run report has no `arch`.** P2. Problem: G-05 and G-06 ask `arch` in each report; `RunReport` and `PublicReport` of pod-job (`crates/pod-job/src/report.rs`, podcrates `v0.70.0`) have none, and T-497's Decision does not list it. Approach: add `arch` to the names of T-508/COORD-087, ask podcrates to add it to T-923 (optional field, `v1` keeps its id), fill it from the kind's `capability.arch` in slots, test it in `cargo test -p podrunner-slots report`.
2. **G-12: a unit over its memory limit does not end with `limit`.** P2. Problem: G-12's acceptance wants `exit_reason: limit` for a job that allocates past `memory`; the podvm kind gives `ENOMEM` to one process (rlimit), incus and microvm give an OOM kill, and `ExitReason::Limit` comes only from the disk check (`crates/podrunner-slots/src/disk.rs:66`). Approach: read the OOM facts of each kind (`memory.events` `oom_kill` of the leaf where a cgroup exists, the instance state of incus, the guest exit of microvm) at the end of a unit, and report `limit` with an audit line `limit memory`; where podvm gives no fact, ask podvm. Prove on real units in `runner-image.yml`.
3. **Disk limit of an offer overrides the operator's bound.** P2 (defect, G-18/G-12). Problem: `crates/podrunner-slots/src/disk.rs:61` takes `limits.disk` of the offer before `disk_max_bytes` (`.or`), and `docs/configuration.md:52` says "a disk limit of the offer comes first"; for memory, CPU, pids and wall the unit takes the lesser (T-198), and an offer may only narrow (T-107). A source can raise a unit's disk above the operator's ceiling. Approach: take the lesser of both; a test with an offer `disk` above `disk_max_bytes`.
4. **G-09: no CI proof of a `docker build` step and a Docker-in-Docker step.** P2. Problem: the parity suite (`crates/podrunner/tests/local/parity/`) proves `services:`, a job container, Docker actions and Dockerfile actions; no step runs `docker build` or `docker run` against `DOCKER_HOST`; `docs/container-engine.md` step 4 is still "Open". Approach: add `10-docker-in-docker.yml` (a `docker build` of a small Dockerfile and a `docker run` of it in a step) to the engine run of `runner-image.yml`.
5. **G-09: the engine comes from a host directory, not the payload image.** P3. Problem: G-09 says "the engine is part of the payload image, not fixed by the host"; `[unit.microvm] engine = DIR` mounts static binaries of the host. Approach: record the call (or put the engine into `runner-full` and make `engine = image`) in `docs/decisions.md`, and tell githome.
6. **G-13: events kept out by Q5, no swappable rule, case table not released.** P2, owner question. Problem: G-13 asks each GitHub event by name, `pull_request_target` from the base branch, and a swappable module; ruling Q5 allows four extra events and never trusts `pull_request_target`; the case table (`crates/podrunner-tier/tests/cases.json`) is not a release asset that githome can run. Approach: write the question with a recommendation for the owner (Q5 is a ruling), set that part `blocked`; ship `cases.json` with T-511.
7. **G-03: the report does not say that a step can read the credential.** P3. Problem: G-03 asks the report to say so; only SPEC §5 and `kinds[].probe.secret_delivery` do. Approach: document it in `docs/contracts/source-driver.md` (the `report` section) or ask podcrates for an optional field; or record that the capability in `status` meets the clause.
8. **G-06: no test of `cpu_s` against a known CPU burn on podvm and microvm.** P3. Problem: the acceptance needs a tolerance; the schema defines none and `the_report_of_a_unit_that_spins_has_its_cpu_time_and_memory` checks only `> 0`. Approach: a known burn (for example 5 s of one core) in `runner-image.yml` on each kind, with a tolerance written in the contract.
9. **G-12: `pids` of the podvm kind is per user, not per unit.** P3. Problem: `RLIMIT_NPROC` counts each process of the user, also other units (`docs/configuration.md`, limits table). Approach: `pids.max` in the delegated cgroup leaf (the T-221 path) where the host delegates one.
10. **G-31: stale schema copies with the same ids.** P2. Problem: `docs/design/schemas/{job-offer,run-report,run-report-public,unit-capability}.v1.schema.json` differ from pod-job's files of the same id (the design run report has `arch`, `bytes_in`, `bytes_out`, `image_digest`, `limits_applied` ...); githome pins schemas by id (G-31). Approach: remove them or mark them as the design input and point to pod-job's `schemas/`.
11. **G-34: podrunner does not plan to adopt the signed release index of `pod-release`.** P2, blocked on podcrates T-104/T-880. Approach: when the crate tags, write the index in `release.yml` and name its verifier in `docs/install.md`; T-484 stays the interim.
12. **G-35 (and G-04 P2): the podrunner half of placeholders.** P3, blocked on podcrates T-100. Problem: the offer policy cannot name a placeholder, and path rules are refused (`egress-policy-unsupported`).
