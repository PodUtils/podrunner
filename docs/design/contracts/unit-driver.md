# Unit driver contract, version 1

A unit driver starts, supervises and destroys one isolated unit for one job. `slots` is the only caller.

Form. The day-one form is a Rust trait in the `podrunner` crate with the operations below, and the conformance suite runs against the trait (SPEC §4.2). This file defines the postconditions of the trait. It also defines a JSON-lines wire for out-of-tree drivers: an executable named `podrunner-unit-KIND`. The wire is built when the first out-of-tree driver exists. Nothing in the core depends on which form a driver takes.

## Conventions

- Wire transport: JSON lines on stdin and stdout, UTF-8, one object per line, no line over 1 MiB. Every object starts with `"schema": 1` and has an `"op"`. Requests carry an `"id"` (string) that the answer repeats. stderr is free text for humans and is never parsed.
- Requests may overlap. Answers may arrive in any order and are matched by `id`. `wait` blocks for up to its `timeout_s` while `signal` for the same unit goes through.
- One driver process serves one host and many units. Paths in a request are relative to the directory given to the driver at spawn (`--workdir DIR`).
- Error answer: `{"schema":1,"id":"..","ok":false,"error":"<code>","detail":"<text>"}`. `error` is a refusal code of SPEC §11.1 or one of `bad-request`, `unknown-unit`, `internal`. A request with an unknown `op`, a missing field or a wrong type is answered with `bad-request` and the driver keeps running. A driver that cannot continue exits with the code of the `pod-core` class that names the cause (T-101) and prints one line to stderr.
- Identifiers. A `unit` id is generated by `slots` as `u-` plus a counter that is unique for the boot id of `slots`. It is never derived from a `job_id`. Every path built for a unit uses only the unit id. A `job_id` is data of the form `[A-Za-z0-9._-]{1,128}` and never a path component.
- Time is RFC 3339 in UTC.
- A capability that is not proven is `unknown`. A consumer treats `unknown` as absent.

## Operations

### probe

```
{"schema":1,"op":"probe","id":"1"}
{"schema":1,"id":"1","ok":true,"capability":{ ...unit-capability.v1... }}
```

No state change. Idempotent. The record has the fields of `schemas/unit-capability.v1.schema.json`: `kind`, `arch`, `boundary`, `boundary_proof`, `principal`, `container`, `net`, `secret_delivery`, `credential_store`, `mount_modes`, `rootfs_fresh`, `tree_kill`, `limits` (each of `cpu`, `memory`, `disk`, `pids`, `wall`), `egress_hold` and `kvm`. The boundary order is `none` < `redirect` < `confined` < `guest`. `boundary_proof` says how the boundary was verified on this host. A driver that did not verify answers `unknown`. A `guest` claim carries the result of the start-up self-test of SPEC §6.6. `principal` says whether units get distinct principals. `credential_store` says what holds the credential directory. `mount_modes` lists the modes the driver enforces. A limit is `enforced` (the runtime stops the job at the limit), `reported` (the driver measures it and `slots` acts) or `none`. `rootfs_fresh` and `tree_kill` are `verified` after the conformance test passed, `none` after it ran and failed, and `unverified` before it ran.

### prepare

```
{"schema":1,"op":"prepare","id":"2","image":"registry.example/runner@sha256:<64 hex>","platform":"linux/amd64","emulate":false}
{"schema":1,"id":"2","ok":true,"image_id":"sha256:<64 hex>"}
```

The payload image is resolved by digest. A tag is refused. A platform that differs from the host's is refused unless `emulate` is true (G-05). `slots` calls `prepare` between `matched` and `claimed` and caches the answer for each digest. The image age comes from the pin and never from the image (SPEC §11.3).

### start

```
{"schema":1,"op":"start","id":"3","unit":"u-0001","image_id":"sha256:...","argv":["./run.sh"],"env":{"K":"V"},
 "mounts":[{"host":"cache/trusted/org-a/npm","guest":"/work/.npm","mode":"ro"}],
 "credential_dir":"state/creds/u-0001","runner_root":"/runner",
 "egress":{"kind":"unix","path":"egress/u-0001.sock"},"control_socket":"state/ctl/u-0001.sock","registries":["ghcr.io"],
 "limits":{"wall_s":3600,"memory_mib":4096},"limits_required":["wall"]}
{"schema":1,"id":"3","ok":true,"started_at":"2026-11-10T09:00:00Z"}
```

Postconditions:

1. A fresh root for this unit. No state shared with another unit of the same image. The podvm driver gives each unit its own `PODVM_STORE` under the state directory and loads the image into it, because all containers of one image in one store share one mutable rootfs today.
2. `credential_dir` was created by `slots` with mode 0700 and holds the credential files with mode 0600. Before the payload starts, the driver copies the files into `runner_root`, which is the unit's workspace root, with mode 0600 and the owner of the payload. The runner is then started with no credential in argv and none in `env`. There is no operation that puts files into a running unit.
3. `destroy` removes `credential_dir` and the copies. `credential_store` says whether that is a tmpfs.
4. A limit in `limits_required` that the driver cannot enforce or report is refused with `limit-not-enforceable`.
5. `egress` and `control_socket` are the only channels the unit gets to the host. `egress` is one of the three forms below. The unix form is bound by `egress.load` to one listener for this unit, so the socket is the identity and no token reaches the unit.
6. The environment never carries the runner credential. The one named exception is the egress token as the proxy password of a `podvm` unit whose hold is `none` (SPEC §9.1). `slots` passes the start environment in `env`, including `DOTNET_EnableWriteXorExecute=0` for the official runner (SPEC §10.3), so an image cannot drop it. The `runner_root` of the example is not a requirement.
7. `control_socket` serves only operations on this unit's containers, validated on the host side (below).
8. `registries` lists the registry hosts that the source allows for job images (SPEC §7.2). An empty list allows no job image.
9. Every process that the driver starts for the unit (the shim, the top process, every container) carries `PODRUNNER_UNIT` with the unit id in its environment. A step can clear the variable in a child, so it is an aid for the leak scan of `destroy` and never proof of emptiness.

The `egress` object is one of these three forms:

```
{"schema":1,"op":"start","id":"3a","unit":"u-0002","image_id":"sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","argv":["./run.sh"],"env":{},"mounts":[],"credential_dir":"state/creds/u-0002","runner_root":"/runner","egress":{"kind":"unix","path":"egress/u-0002.sock"},"control_socket":"state/ctl/u-0002.sock","registries":[],"limits":{"wall_s":600},"limits_required":[]}
{"schema":1,"op":"start","id":"3b","unit":"u-0003","image_id":"sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","argv":["./run.sh"],"env":{},"mounts":[],"credential_dir":"state/creds/u-0003","runner_root":"/runner","egress":{"kind":"tcp-loopback","host":"127.0.0.1","port":3128},"control_socket":"state/ctl/u-0003.sock","registries":[],"limits":{"wall_s":600},"limits_required":[]}
{"schema":1,"op":"start","id":"3c","unit":"u-0004","image_id":"sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","argv":["./run.sh"],"env":{},"mounts":[],"credential_dir":"state/creds/u-0004","runner_root":"/runner","egress":{"kind":"vsock","cid":3,"port":8080},"control_socket":"state/ctl/u-0004.sock","registries":[],"limits":{"wall_s":600},"limits_required":[]}
```

### signal

```
{"schema":1,"op":"signal","id":"4","unit":"u-0001","signal":"TERM"}
{"schema":1,"id":"4","ok":true}
```

Reaches every process of the unit, not one pid. A signal name that the unit kind does not have is `bad-request`. The podvm driver starts one subreaper shim for each unit as the parent of the unit's top process, so orphans reparent to that unit's shim and `signal` and `destroy` walk the shim's descendants (SPEC §10.4). Containers that `container_start` creates are spawned through the same shim (the driver sends the spawn request over a pipe that the driver holds; a process of the same uid can reach it where ptrace or proc access is allowed, as for the control socket, SPEC §5.3; Inferred), so they are descendants of it too.

### wait

```
{"schema":1,"op":"wait","id":"5","unit":"u-0001","timeout_s":30}
{"schema":1,"id":"5","ok":true,"done":true,"report":{"exit_code":0,"exit_reason":"done","wall_s":61.2,"cpu_s":"unknown","peak_rss_mib":"unknown","bytes_in":"unknown","bytes_out":"unknown","limits_applied":["wall"]}}
```

`done` is false when `timeout_s` elapsed first. `exit_reason` is one of `done`, `cancelled`, `timeout`, `limit`, `unknown_end`. `slots` owns the wall clock: it sends `signal`, waits the grace period and calls `destroy`. The `wall_s` of `start` is advisory. A driver reports `wall: enforced` only when its runtime itself kills the job. `lost` is a state of `slots` and the driver never reports it. `unknown_end` means the driver lost track of the unit, and `slots` maps it to `lost`. The death of the shim before the top process ends is `unknown_end`.

### destroy

```
{"schema":1,"op":"destroy","id":"6","unit":"u-0001","deadline_s":60}
{"schema":1,"id":"6","ok":true,"residual_processes":0,"residual_files":0}
```

After the answer no process descended from the unit exists and no file of the unit remains. The driver stops every container id it recorded for the unit, walks the shim's descendants, and counts both processes and files. A nonzero count is `"ok":false`. Destroying an unknown unit is `unknown-unit`.

If the shim is not alive at `destroy`, the driver cannot prove that no process remains. It kills the processes that carry the unit's `PODRUNNER_UNIT` marker (never by argv word), and answers `residual_processes` as the string `unknown` with `"ok":false`:

```
{"schema":1,"id":"6b","ok":false,"error":"internal","detail":"shim not alive","residual_processes":"unknown","residual_files":0}
```

`slots` treats `unknown` as above 0, and the host enters `degraded` (SPEC §10.4).

## Container operations

The hook path (SPEC §7.2, `hook.md`) and the control socket server (SPEC §7.2) call these. Each is scoped to one unit: a request names `unit` and a container id that the same unit created. The driver refuses any other id with `unknown-unit`. A driver reports `container: none` when it has none of them.

| Operation | In | Out |
| --- | --- | --- |
| `container_start` | `unit`, `name`, `image` (a tag is allowed), `entrypoint`, `args`, `env`, `workdir`, `ports`, `mounts`, `network_alias` | `container` id, `digest` the image resolved to at pull, `ports` as bound. The container is spawned through the unit's shim |
| `container_exec` | `unit`, `container`, `argv`, `env`, `workdir`, `stdin: bool` | `exec` id and a stream (below). A driver that reports `container: hook` over podvm refuses `stdin: true` and returns one stream (id 1), because `podvm exec -i` is a no-op and `logs` is one interleaved file |
| `container_logs` | `unit`, `container`, `follow: bool` | a stream |
| `container_inspect` | `unit`, `container` | `state`, `health`, `env`, `ports`, `network` |
| `container_stop` | `unit`, `container`, `deadline_s` | `ok` |

A tag in `image` is resolved to a digest by the driver at pull time, through the egress path and the registry hosts of the policy. The driver returns the digest and `slots` records it in the report (`job_images`). The payload image of `prepare` must be a digest. Environment and working directory are always passed in and never inherited (podvm's `exec` inherits neither today).

### Streams

A stream is carried on the unit's control socket (below), not in a JSON line. It is a sequence of frames: a 4 byte big-endian length `N` of the rest, one byte stream id (1 stdout, 2 stderr, 3 stdin, 4 exit status), then `N - 1` bytes of data. The exit status frame holds a decimal exit code and ends the stream. A frame has at most 1 MiB of data.

## The control socket of one unit

`start` gives each unit one unix socket. It speaks HTTP/1.1 with JSON bodies, so a script can call it with `curl --unix-socket`. The routes are the five container operations (`POST /v1/container/start` and so on), `POST /v1/exec` (the framed stream as the response body), `POST /v1/hook/COMMAND` (the runner's hook input unchanged, SPEC §7.2) and `POST /v1/job_state` with `{"event":"job-started"}` or `{"event":"job-completed"}`, accepted once for each event and audited. `job-started` is accepted only in state `started`. `job-completed` records the time and changes nothing else: the state `ended` follows only from the exit of the top process (`wait`), from `signal` or from `destroy`, so a step cannot end its own job as `done`.

The socket is served by the host-side `ctl` module, never by the script in the unit. A process of the unit in the same uid can call it, so **the server applies the closed field set of `hook.md` to every request, before the driver acts**. The hook script is a relay, and any check it makes only clarifies the job log.

The server cannot tell the runner's `prepare_job` from one that a step posts: both arrive on the same socket from the same uid. So the rule on images below is not a boundary. It bounds a request to the registries of the source and to the egress policy. The mount table, the port rule and the refusal of devices, privileged flags and host paths do not depend on who sent the request, and the server enforces them. They are the real controls.

- **Order.** `prepare_job` is accepted once for each unit, in state `started` or `running`, before any `run_script_step` or `run_container_step`. A second `prepare_job`, or one after a step command, is refused with `container-option-refused` and the field `command`, and audited. Until the first `prepare_job` was accepted, every container operation and every hook route except `cleanup_job` is refused the same way. A job with no `container:` and no `services:` never gets a `prepare_job` from the runner (Source, `JobExtension.cs` of actions/runner main, read 2026-11-10), so the server refuses every container operation of such a job. That includes the container actions of the job.
- **Images.** `container_start` accepts an image only if its registry host is in `registries` of the `start` request. The registry host is the part before the first `/` when that part holds a `.` or a `:` or is `localhost`, and `docker.io` otherwise. A forged `prepare_job` can therefore name only an image of an allowed registry, which a step can fetch through the egress policy anyway. The same rule applies to the image of a `run_container_step`.
- **Mounts** come from a fixed table, matched by exact target string. The hook route picks the table by its command: `prepare_job` uses the job container table and `run_container_step` the container action table, and a target of the other table is refused. A `container_start` posted to its own route is checked against the union of the two tables. A `services:` container has no system mounts, so every mount on it is refused. The source of each entry is a directory under the unit's own state that `start` created and `destroy` removes. The server resolves it with `RESOLVE_BENEATH` and passes the resolved path of an open descriptor (`/proc/self/fd/N`, inherited by the spawned process) if podvm accepts one (Unverified, U25). If podvm does not, the check is one made at one time and not a binding, and the server re-checks every component of the source with `lstat` immediately before the spawn. No host path, no device, no privileged flag, no network mode but the default.
- **Ports.** A `container_start` with `ports` is refused with `container-option-refused` on a `net: shared-host` unit. On `net: private` it is accepted only with `HostIp` set to loopback. Port claims are deferred (SPEC §15).
- The system mount `/var/run/docker.sock` is accepted and dropped. The entry is matched when both its source and its target are that literal string. An entry that names the path on one side only is refused, like every other socket bind.
- A registry credential is accepted only if the host of its `serverUrl` equals the registry host of the image it came with.
- Every other field and every route not listed is refused with `container-option-refused` and the field name.
- A request names a container id that the same unit created. Another id is `unknown-unit`. The socket cannot reach the `slots` control socket (SPEC §11.5).

The mount table. The job container table, for `prepare_job`. Each source is a directory under `runner_root` and is created at `start`.

| Target in the container | Source under `runner_root` | Mode |
| --- | --- | --- |
| `/__w` | the work directory | rw |
| `/__w/_temp` | `_temp` of the work directory | rw |
| `/__w/_actions` | `_actions` of the work directory | rw |
| `/__w/_tool` | `_tool` of the work directory | rw |
| `/__e` | `externals` | ro |
| `/github/home` | `_github_home` of `_temp` | rw |
| `/github/workflow` | `_github_workflow` of `_temp` | rw |

The entries are those that the runner adds to a job container when container hooks are on (Source, `MountWellKnownDirectories` of `ContainerOperationProvider.cs`, actions/runner at `310a370bf360`). `/__e` is read-only there on Linux. The tool cache row is `/__w/_tool` because `HostContext.cs` puts the tool directory at `_tool` of the work directory when `RUNNER_TOOL_CACHE`, `RUNNER_TOOLSDIRECTORY` and `AGENT_TOOLSDIRECTORY` are all unset, and `ContainerInfo.cs` maps the work directory to `/__w` before the tool directory. The runner uses the target `/__t` only when one of those variables names a directory outside the work directory. `start.env` sets none of them (SPEC §10.3), so the table has `/__w/_tool` and a request with `/__t` is refused. An image whose own environment sets one of them is Unverified (U19). No entry names a directory outside the unit.

The container action table, for `run_container_step`. The runner builds a Docker action's container with other mounts (Source, `ContainerActionHandler.cs`, same pin). Each source is a directory under `runner_root`.

| Target in the container | Source under `runner_root` | Mode |
| --- | --- | --- |
| `/github/runner_temp` | `_temp` of the work directory | rw |
| `/github/home` | `_github_home` of `_temp` | rw |
| `/github/workflow` | `_github_workflow` of `_temp` | rw |
| `/github/file_commands` | `_runner_file_commands` of `_temp` | rw |
| `/github/workspace` | the workspace directory of the job, under the work directory | rw |

The runner sets the working directory of a container action to `/github/workspace`. The system mount `/var/run/docker.sock` is added to a container action as to a job container and is accepted and dropped by the rule above.

A microVM driver has no such socket until a guest runner image exists: it reports `container: none` (SPEC §7.2). The in-image hook decodes frames in bash. Whether that is workable is Unverified (WP-13). If it is not, the socket serves a plain mode: stdout of the exec as the response body, stderr appended to the unit log, the exit code from `GET /v1/exec/ID`.

## Conformance suite

Every driver passes these before `slots` trusts it. Each is a test with a planted defect and a correct input. A driver that fails test 2, 3 or 15 reports `rootfs_fresh` or `tree_kill` as `none`, and one that has not run them reports `unverified`. `slots` treats both as not verified, refuses jobs whose `limits_required` names `wall`, and the report states it.

1. `probe` twice gives the same record, and no process or file appears.
2. `start` of two units from one image: a file written by one is not visible to the other, and `/etc/hosts` of one does not contain a name written by the other.
3. A unit that forks a grandchild that calls `setsid` and sleeps: `destroy` returns `residual_processes: 0`, within the deadline. The same with the grandchild forked inside a container that `container_start` created and inside a service container: a naive kill of the top process leaves them, `destroy` does not.
4. `start` with a limit the driver cannot enforce, listed as required: refused by name.
5. A tag instead of a digest in `prepare`: refused. A foreign platform with `emulate: false`: refused.
6. The credential directory is absent from the host filesystem after `destroy` (host scan, positive control: the scan finds a planted file).
7. A step that dumps `/proc/*/cmdline` and `/proc/*/environ` finds no byte of the credential files (positive control: the dump finds a planted blob in an env scenario).
8. `container_exec` with an environment variable and a working directory: the command sees both.
9. The control socket of unit A refuses a container id of unit B.
10. A `boundary_proof` that carries a planted credential canary is detected by the scan of all driver outputs.
11. A `guest` driver that is really a plain process fails the start-up self-test (SPEC §6.6), and a real guest passes it.
12. `job_id` `../x` never appears as a path component.
13. A `container_start` posted straight to the control socket with a `mounts` entry for `/`, with a privileged flag, with `ports` on a `net: shared-host` unit, and with an image of a registry outside `registries` is refused with `container-option-refused`. A valid runner request, including the `/var/run/docker.sock` system mount and the seven entries of the job container table, passes and mounts nothing for the docker.sock entry. An entry that names the docker.sock path as source only is refused. A mount table entry with a source outside the unit's directory, or `/__e` as `rw`, is refused. The tool cache entry `/__w/_tool` passes and `/__t` is refused.
14. `POST /v1/job_state` with `job-started` moves the job once. A second post is ignored and audited. A `job-started` in state `running` is ignored. A `job-completed` posted while the job runs records the time and leaves the state unchanged.
15. A step kills the shim with SIGKILL, then `destroy` is called: it must not report `residual_processes` 0. It answers `unknown` and `"ok":false`.
16. A second `prepare_job` naming a new image is refused, and a `container_start` of that image is refused. A `container_start` and a `run_container_step` before any `prepare_job` are refused. A `prepare_job` after a `run_script_step` is refused.
17. A `run_container_step` that carries the five entries of the container action table and the docker.sock system mount passes. The same request with a job container target (`/__w`) is refused, a `prepare_job` with a container action target (`/github/workspace`) is refused, a source outside the unit's directory is refused, and a mount on a `services:` container is refused. Every refusal is `container-option-refused` with the field name.
