A beta of podrunner, for tests. It is not for production CI.

podrunner runs each CI job of GitHub (or of another forge) in one fresh
unit and destroys the unit after the job. It needs no root and no
docker daemon. Each binary is static (musl).

Each claim below ends with the level of its proof, in square brackets:
`[CI]` is proven in CI on GitHub-hosted runners, `[user]` is proven on a
constrained host as a user, and `[not run]` is not run. A claim with no
bracket is not a claim of behavior. The sections "What is proven in CI",
"What is proven on a constrained host as a user" and "What is not
proven" give the runs and the hosts.

## Quick start of the local mode

```sh
curl -fsSLO https://github.com/PodUtils/podrunner/releases/download/v0.1.0-beta.8/podrunner-install.sh
sh podrunner-install.sh
cd YOUR-PROJECT && podrunner run .github/workflows/ci.yml --checkout .
```

The installer downloads podrunner, podvm, podnet, the official runner and
the runner image, checks each SHA-256 against the pins of this release,
loads the image, and writes `run.toml`. A second run downloads nothing.
With no network: download `podrunner-bundle-ARCH.tar.gz`, unpack it, and
run `sh podrunner-install.sh --bundle .` in it (`docs/install.md`). The
install from the release URL has never run against a published release
(see "What is not proven"); the lanes of the user-path gate run the same
steps from a local HTTP server with the paths of the release.

## Breaking changes

No compatibility with a released binary is owed (`AGENTS.md`, section
2). These changes can break a script or a file that runs with
`v0.1.0-beta.7`:

* A command that takes no such flag refuses it with exit 64:
  `drain`, `stop`, `resume` and `clear-degraded` take no `--json` (their
  answer is JSON); `status` and `clear-degraded` refuse `--source`;
  `serve --json` is refused; `--state` with `--socket` (also
  `audit verify --state` with `--file`) exits 64; `run --microvm` with
  `--incus` exits 64; `run --web` with `--dry-run` exits 64; a value of
  `--changed-since` or `--remote` that starts with `-` exits 64; `image
  verify --arch` with an unknown value exits 64 (it was 78). Each
  executor of the command line drops the keys of the files of `run` that
  belong to another executor.
* `check` of a file with a `microvm` or `incus` kind on a host that
  cannot run it prints `podrunner: [unit.microvm]: not here: WHY` on
  stderr and counts the kind in, so the verdict is the same on each host.
  `check --here` and `serve` count the kind out: a file whose sources
  only that kind serves exits 75 (it was 78). `config init` refuses a
  `microvm` kind on a host with no `/dev/kvm` that opens for reading and
  writing.
* `head_is_fork` has one meaning: the head repository is another
  repository than the repository of the job (`yes`), the same one
  (`no`), or not known (absent). It is not the `fork` flag of the head.
  For an event that is not a pull request, it is `no`.
* A job of an agent (T-106) goes to a guest only with `head_is_fork =
  no`. An agent job of another event than `pull_request` from a fork,
  and one with an unknown head, are `event-not-allowed`.
* The directories of a run in `TMPDIR` are `podrunner-run-tree-NS-PID-N`
  and `podrunner-run-units-NS-PID-N` (the probe: `podrunner-probe-NS-PID-N`).
  A script that reads the old names must change.
* `doctor --json` gives each source `extra_permissions` (a list).
* The work folder of the runner in a unit is `/home/runner/work` in place
  of `_work`. `work_folder = "/home/runner/_work"` gives the old folder.
* The control socket speaks `pod-control` protocol 1: a client of
  `{"v":1,"op":...}` gets `bad-request` (`docs/cli.md`).
* `print-unit` refuses a relative `--config` or `--state`, and writes
  `RestartPreventExitStatus=64 78` and the new hardening lines.
* A signed pin list with `sandbox = true` must be signed again
  (`podrunner pin-sign`).
* A unit with no `[egress] default_policy` has no way out, also for an
  offer of `mode: open`.

## What is not proven

  real GitHub: only a fake scale-set service and a fake API ran. The live
  lane for the re-offer of queued jobs after a kill is open (T-621).
* The live gates (T-032, T-033, T-040; GitHub #74 and #75).
* The peak memory and the OOM kills of an incus instance: podvm
  `0.2.0-beta.39` gives none for a stopped instance, so the report says
  `unknown` and 0 OOM kills with a reason (T-611, blocked on COORD-128,
  GitHub #350; podvm fixed it after the release `0.2.0-beta.39`).
* The `microvm` and `incus` kinds on the host of a user: the QA hosts had
  no KVM and no incusd. The kinds ran on GitHub-hosted runners only
  (`runner-image.yml`, the lane `serve-incus-kvm`).
* The cancel of a `container:` job (T-639) on podvm: the proof is a fake
  unit (the lane T-644 is open). `actions/checkout` with `ref:` (T-640)
  on `--podvm`.
* The online install from the release URL: the files of this release do
  not exist before the release. The lanes of the gate install from a
  local HTTP server with the same paths. The signature of a published
  release (`pod-release verify`, `cosign verify-blob`) and the push of
  the images to ghcr.io have not run; the first run is this release.
* aarch64 on a host of a user. aarch64 is built, and
  `runner-image.yml` builds its runner image in CI.
* `busybox sh` for the installer.
* The man page: no groff or mandoc check, and no release asset (T-645).
* A real client through a placeholder credential, a JVM client with the
  trust store (T-577), the start of `serve` in a unit of the system
  (T-588), and two pid namespaces on a hosted runner (T-607).
* The areas that the QA round did not test (T-637): among them `--engine`,
  `services:`, Docker actions, `--vnet`, `--full`, OIDC, `--protected`,
  `--schedule`, `--break` and a real full disk.
* A podvm unit off the namespace rung (the loader and supervise rungs, as
  on Ubuntu 24.04, where AppArmor restricts user namespaces) has no PID
  namespace: a job sees the processes of the host and can send a signal
  to each process of your user. `podrunner doctor --run` names the rung.
  For a job that you do not trust there, use `--microvm`.
* In a podvm unit, the tests of pallets/click (uv) and the lint of rq/rq
  (ruff) can fail with EACCES at the persist of a temporary file (T-261,

| `scaleset-sidecar-aarch64-unknown-linux-musl` | the sidecar, Linux ARM64 |
| `podrunner-install.sh` | the installer of the local mode, with the pins of this release |
| `podrunner-bundle-x86_64.tar.gz`, `podrunner-bundle-aarch64.tar.gz` | each file that the installer takes, for a host with no network |
| `runner-x86_64.tar`, `runner-aarch64.tar` | the runner image, for `podvm load -i` |
| `runner-full-x86_64.tar`, `runner-full-aarch64.tar` | the larger runner image (`images/runner/full.txt`) |
| `podrunner-manifest.json` | the versions, each binary and each runner image with its digest, its size unpacked and `built_at_s` |
| `tier-cases.json` | the case table of the tier rule (`docs/install.md`, "The release assets") |
| `release-index.json`, `SHA256SUMS`, `SHA256SUMS.sigstore.json` | the index of the release and the signed sums |

Each file has a `.sha256` file and a build provenance attestation. The
release is also on ghcr.io (`ghcr.io/podutils/podrunner:v0.1.0-beta.8`
and `ghcr.io/podutils/podrunner-runner:v0.1.0-beta.8`); the section "The
images, by digest" of the release gives each digest.

```sh
sha256sum -c podrunner-x86_64-unknown-linux-musl.sha256
gh attestation verify podrunner-x86_64-unknown-linux-musl --repo PodUtils/podrunner
pod-release verify --repo PodUtils/podrunner --tag v0.1.0-beta.8
```

A unit also needs:

* podvm `v0.2.0-beta.39` (`images/podvm.toml` gives the SHA-256 of each
  binary); the `microvm` kind needs QEMU and `/dev/kvm`, and the `incus`
  kind an incusd;
* podnet `v0.4.0-beta.17` for the egress hold of the podvm kind
  (`images/podnet.toml`);
* the runner image: the asset `runner-ARCH.tar` (`podvm load -i`), or a
  build of `images/runner/Dockerfile`; the official runner is `2.338.2`.
