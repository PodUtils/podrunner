A beta of podrunner, for tests. It is not for production CI.

podrunner runs each CI job of GitHub (or of another forge) in one fresh
unit and destroys the unit after the job. It needs no root and no
docker daemon. Each binary is static (musl).

## What is new since v0.1.0-beta.2

* The `program` source kind (`docs/configuration.md`, "A program
  source"): any program that speaks the source wire on its stdio serves
  jobs, as the scale-set sidecar does for GitHub. A forge ships its own
  program; podrunner adds no code for it.
* `podrunner source-conformance -- PROGRAM ARGS...`: the 12 tests of the
  source wire against such a program. A forge runs it in its own CI.
* The `microvm` kind (`[unit.microvm]`): a guest of the machine tier of
  podvm for each job, its own kernel under KVM, no NIC. Its one way out
  is a channel to the egress socket of the unit, and the job gets that
  address as its proxy. The kind claims `guest`, and `serve` takes the
  claim only after the self-test of the guest. It is the unit of the
  `untrusted` tier (a fork pull request).
* The `incus` kind (`[unit.incus]`): a system container of the incus
  tier of podvm for each job. It claims `confined`, the floor of
  `trusted`.
* The egress policy of an offer narrows `[egress] default_policy`: an
  offer can take away, never add. A policy with a path rule is refused
  (`egress-policy-unsupported`).
* `[trust] extra_events`: the operator may let `workflow_run`,
  `issue_comment`, `release` and `repository_dispatch` jobs be trusted.
  A job of an `agent` actor runs as `untrusted`; a `bot` is never
  trusted.
* The guest self-test needs a kernel of its own: the boot id and
  `/proc/version` both differ from the host's.

## What is proven in CI

* The local mode (`podrunner run workflow.yml`) and the podvm kind, as
  in beta.2, now on podvm `v0.2.0-beta.10`.
* The `microvm` kind on real guests under KVM: the guest self-test, 11
  unit conformance tests, and the official runner v2.338.2 completing a
  job of the fake broker through the egress channel.
* The `incus` kind on real instances of incus 6.0: 13 unit conformance
  tests.
* The `program` source: the 12 source tests against
  `podrunner fake-source`.

## What is not proven

* No job of real github.com or of githome ran yet. The live gates
  (T-032, T-033, T-040) run on test hosts with this beta.
* The `microvm` and `incus` kinds have no container route: a
  `container:` job or a Docker action waits for T-103.
* A report of this beta does not carry `cpu_s` or `peak_rss_mib`; T-108
  adds them after it.

## The files

| File | What it is |
| --- | --- |
| `podrunner-x86_64-unknown-linux-musl` | podrunner, Linux x86-64 |
| `podrunner-aarch64-unknown-linux-musl` | podrunner, Linux ARM64 |
| `scaleset-sidecar-x86_64-unknown-linux-musl` | the sidecar of a `github-scaleset` source, Linux x86-64 |
| `scaleset-sidecar-aarch64-unknown-linux-musl` | the sidecar, Linux ARM64 |

Each file has a `.sha256` file and a build provenance attestation.

```sh
sha256sum -c podrunner-x86_64-unknown-linux-musl.sha256
gh attestation verify podrunner-x86_64-unknown-linux-musl --repo PodUtils/podrunner
```

A unit also needs:

* podvm `v0.2.0-beta.10` (`images/podvm.toml` gives the SHA-256 of each
  binary); the `microvm` kind needs QEMU, and the `incus` kind an
  incusd;
* podnet `v0.4.0-beta.8` for the egress hold of the podvm kind
  (`images/podnet.toml`);
* the runner image: build it with `images/runner/Dockerfile`, or take
  the archive `runner-x86_64` or `runner-aarch64` of the
  `runner-image.yml` run of the tagged commit, and `podvm load` it.

## Report a problem

Open an issue in `PodUtils/podrunner` with the command, its output, and
the output of `podrunner doctor --json`. Do not put a key, a token or a
credential file in the issue.
